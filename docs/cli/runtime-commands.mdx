# Runtime Commands

Runtime commands let you inspect and control a running PyOrchestrate orchestrator through a ZeroMQ ROUTER/DEALER channel over TCP. They support monitoring, agent lifecycle operations, event history, and graceful shutdown without stopping the application first.

## Prerequisites

The orchestrator command interface must be enabled. It is enabled by default, but configuring it explicitly makes the runtime endpoint clear:

```python
from PyOrchestrate.core.orchestrator import Orchestrator

config = Orchestrator.Config(
    enable_command_interface=True,
    command_zmq_address="tcp://127.0.0.1:5555",
)

orchestrator = Orchestrator(config=config)
```

`tcp://127.0.0.1:5555` is the default on both sides: the orchestrator binds it, and CLI clients connect to it. The snippet above spells it out, but an orchestrator that says nothing about `command_zmq_address` binds the same address.

<Warning title="Network exposure">
Binding anything but loopback — `tcp://*:5555` covers every network interface — exposes the command interface to other hosts, and it authenticates nobody: whoever reaches the port can run every command in `allowed_commands`, `shutdown` included. The orchestrator logs a warning at startup when the address it binds is reachable from other hosts.
</Warning>

## Command Syntax

```bash
pyorchestrate <command> [arguments] [options]
```

Most runtime commands accept:

- `--socket ZMQ_ADDRESS`: ZeroMQ address used by the client. Default: `tcp://127.0.0.1:5555`
- `--format {table,json}`: Output format. Default: `table`

The option is named `--socket` for CLI compatibility, but its value is a ZeroMQ TCP address rather than a filesystem socket path.

## Output Formats

Table output is designed for interactive use:

```bash
pyorchestrate ps
```

JSON output is useful for scripts:

```bash
pyorchestrate ps --format json
```

Successful JSON responses contain the command data directly, without an outer `status` or `data` wrapper:

```json
{
  "agents": [],
  "running_count": 0,
  "max_workers": 5,
  "waiting_count": 0
}
```

Errors retain their structured error response, described in
[Error Responses](#error-responses).

## Error Responses

A command that fails answers with a structured payload instead of the command
data. `--format json` prints it unchanged:

```json
{
  "status": "error",
  "error": "Agent ghost not found",
  "code": 404,
  "data": {},
  "request_id": "0e5a6e0e-1d1e-4f39-9a2f-2d9a2e5f7c31",
  "timestamp": "2026-01-01T00:00:00",
  "protocol_version": "1.0"
}
```

Table output renders the same payload as a single line, `stats` included:

```text
Error: Agent ghost not found
```

The reason is always carried by `error`, and `code` classifies it:

| Code | Meaning |
|---|---|
| `400` | The command is not recognised, or an agent command arrived without an agent name: `pyorchestrate start` with no argument answers `Unknown command: start` |
| `403` | The command is not in `allowed_commands` — see [`commands`](#commands) |
| `404` | The agent named in the request is not registered |
| `409` | The agent is already active, for `start` |
| `500` | The command failed unexpectedly |

<Note>
  The CLI prints the error and still exits with status `0`. When scripting,
  read `status` from the `--format json` payload rather than the exit status.
</Note>

## Available Commands

| Command | Purpose |
|---|---|
| `ps` | List registered agents and their current state |
| `status` | Show orchestrator status or the status of one agent |
| `dependencies` | Show registered agent dependencies |
| `start` | Start a registered agent |
| `stop` | Stop a registered agent |
| `commands` | List commands allowed by the current orchestrator configuration |
| `history` | Read recent orchestrator events |
| `history-stats` | Show aggregated event statistics |
| `stats` | Continuously refresh agent resource statistics |
| `shutdown` | Request a graceful orchestrator shutdown |

## `ps`

List all registered agents:

```bash
pyorchestrate ps [--socket ZMQ_ADDRESS] [--format {table,json}]
```

Table output includes the agent name, whether it is alive, whether it has been started, and whether it is waiting in the worker queue.

Each entry in the JSON `agents` list also carries `lifecycle_state`, the
parent-process state tracked for that entry: `registered`, `starting`,
`running`, `stopping`, `terminated`, `failed`, or `quarantined`. It is more
precise than `alive`, which only reports whether the thread or process object
is still running. The same field is present in `status AGENT_NAME` and in
`stats`.

An agent that is registered but not yet initialized reports its registered
`config`, or `null` when none was supplied.

## `status`

Show overall orchestrator status:

```bash
pyorchestrate status [--socket ZMQ_ADDRESS] [--format {table,json}]
```

Show one agent:

```bash
pyorchestrate status AGENT_NAME [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The agent form returns the name, `alive`, `lifecycle_state`, `started`,
`in_queue`, and the names the agent depends on:

```json
{
  "name": "consumer",
  "alive": false,
  "lifecycle_state": "registered",
  "started": false,
  "in_queue": false,
  "dependencies": ["producer"]
}
```

An orchestrator JSON response has this shape:

```json
{
  "total_agents": 3,
  "running_agents": 2,
  "max_workers": 5,
  "waiting_agents": 1,
  "command_interface_enabled": true,
  "command_zmq_address": "tcp://127.0.0.1:5555"
}
```

## `dependencies`

Show the dependency mapping for all registered agents:

```bash
pyorchestrate dependencies [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The command reports the mapping held by `DependencyGraph`, the same one used to
compute the startup order:

```json
{
  "dependencies": {
    "consumer": ["producer"]
  }
}
```

Agents without dependencies are absent from the mapping. From in-process code
the same data is available as `orchestrator.dependency_graph.dependencies`.

## `start`

Start a registered agent:

```bash
pyorchestrate start AGENT_NAME [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The agent name is required for the operation to succeed.

The response reports the scheduler outcome rather than assuming success:

```json
{
  "message": "Agent worker-1 start initiated",
  "status": "queued",
  "reason": null
}
```

`status` is one of `started`, `queued`, `cancelled`, `failed_clean`, or
`failed_live`; `reason` carries the failure description when there is one. See
[WorkerPoolScheduler](/advanced/orchestrator-internals/worker-pool) for what
each outcome means for capacity.

## `stop`

Stop a registered agent:

```bash
pyorchestrate stop AGENT_NAME [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The agent name is required for the operation to succeed.

## `commands`

Inspect the command permissions applied by `allowed_commands`:

```bash
pyorchestrate commands [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The result includes allowed commands, restricted commands, and whether restrictions are active.

## `history`

Read recent events from the orchestrator event store:

```bash
pyorchestrate history \
  [--last N] \
  [--agent AGENT_NAME] \
  [--type EVENT_NAME] \
  [--after-seq SEQUENCE] \
  [--socket ZMQ_ADDRESS] \
  [--format {table,json}]
```

Options:

- `--last N`: Maximum number of recent events. The backend default is `100`, and
  a value of `0` or less returns no events
- `--agent AGENT_NAME`: Return events for one agent
- `--type EVENT_NAME`: Return events with one event name
- `--after-seq SEQUENCE`: Return events after a sequence number

Each event returned as JSON includes `seq`, `timestamp`, `t_wall`, `t_mono_ns`, `category`, `event_name`, `agent`, `severity`, and `data`.

Event names are stored as lowercase enum values, for example `agent_registered` and `agent_started`.

The history covers registration events, the lifecycle events routed from the
agents (`agent_started`, `agent_ready`, `agent_heartbeat`, `agent_error`,
`agent_terminated`), and explicit `orchestrator.event_bus.emit(...)` calls.
`agent_error` is stored with severity `ERROR` and carries the reported message
under `data.error_message`.

<Note>
  The store is a ring buffer sized by `history_max_events` (default `5000`), so
  a long-running orchestrator eventually drops its oldest events.
</Note>

## `history-stats`

Show aggregated event-store statistics:

```bash
pyorchestrate history-stats \
  [--agent AGENT_NAME] \
  [--socket ZMQ_ADDRESS] \
  [--format {table,json}]
```

Use `--agent` to limit the statistics to one agent.

The output separates two figures that measure different things:

- **Default buffer** and **Retained in all buffers** count the events still held
  in memory. They shrink back as the ring buffers evict their oldest records,
  and they always cover the whole orchestrator, even with `--agent`.
- **Event Type Breakdown** counts every event *recorded since the orchestrator
  started*, per event name, and honours `--agent`. Its counters never decrease,
  so they exceed the retained figures on a long-running orchestrator.

The breakdown covers every store, including the per-agent one the orchestrator
installs for `agent_heartbeat` — see
[Event Bus](/advanced/orchestrator-internals/event-bus).

## `stats`

Continuously refresh resource statistics for registered agents:

```bash
pyorchestrate stats [--socket ZMQ_ADDRESS] [--interval SECONDS]
```

The default refresh interval is `2.0` seconds. Press `Ctrl+C` to stop monitoring.

Unlike the other runtime commands, `stats` does not expose `--format`; it renders a continuously refreshed table.

A refresh that fails prints the reason reported by the orchestrator, in the
form described in [Error Responses](#error-responses), and the next refresh
tries again. This is what a `stats` left out of `allowed_commands` looks like:

```text
Error: Command 'stats' is not allowed. Allowed commands: ps, status
```

## `shutdown`

Request graceful shutdown of the orchestrator:

```bash
pyorchestrate shutdown [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The command sets the orchestrator shutdown request and returns immediately: the
reply confirms that shutdown was *initiated*, not that it completed.

The request makes `Orchestrator.join()` leave its loop, and the orchestrator
then stops every agent, waits for them within `agent_stop_timeout`
(`10.0` seconds by default), and force-terminates any process agent that
ignored the cooperative stop request. Only afterwards are the message router,
the command interface, and the plugins shut down.

<Warning>
  A thread agent cannot be force-terminated. One that ignores its `stop_event`
  survives the timeout, is quarantined, and is logged as `CRITICAL`; being a
  non-daemon thread, it also keeps the interpreter alive. Always honor
  `control_events.stop_event` in long-running thread agents.
</Warning>

## Connecting to a Different Address

Use the same TCP endpoint configured by the orchestrator. For a local-only listener:

```python
config = Orchestrator.Config(
    enable_command_interface=True,
    command_zmq_address="tcp://127.0.0.1:5555",
)
```

```bash
pyorchestrate status --socket tcp://127.0.0.1:5555
```

For a remote orchestrator, replace the client host with the server address:

```bash
pyorchestrate status --socket tcp://192.0.2.10:5555
```

Ensure the bind address, firewall, and command permissions match the intended exposure.

## Automation Example

Because successful JSON output contains the command data directly, query fields from the root object:

```bash
STATUS=$(pyorchestrate status --format json)
RUNNING=$(echo "$STATUS" | jq '.running_agents')
TOTAL=$(echo "$STATUS" | jq '.total_agents')

echo "Running agents: $RUNNING/$TOTAL"
```

## Troubleshooting

### Cannot connect

Confirm that:

1. the orchestrator process is running;
2. `enable_command_interface` is `True`;
3. the client address points to the configured ZeroMQ port;
4. the port is reachable through the local firewall.

Test the default local endpoint:

```bash
pyorchestrate status --socket tcp://127.0.0.1:5555
```

Check whether a process is listening on the port:

```bash
lsof -nP -iTCP:5555 -sTCP:LISTEN
```

### Command rejected

A rejection answers with code `403` and already lists what is permitted:

```text
Error: Command 'shutdown' is not allowed. Allowed commands: commands, ps, status
```

Inspect the active permissions:

```bash
pyorchestrate commands --socket tcp://127.0.0.1:5555
```

Then update `allowed_commands` in `Orchestrator.Config` if the rejected operation should be permitted.
