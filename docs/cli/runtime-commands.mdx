# Runtime Commands

Runtime commands let you inspect and control a running PyOrchestrate orchestrator through a ZeroMQ ROUTER/DEALER channel over TCP. They support monitoring, agent lifecycle operations, event history, and graceful shutdown without stopping the application first.

## Prerequisites

The orchestrator command interface must be enabled. It is enabled by default, but configuring it explicitly makes the runtime endpoint clear:

```python
from PyOrchestrate.core.orchestrator import Orchestrator

config = Orchestrator.Config(
    enable_command_interface=True,
    command_zmq_address="tcp://*:5555",
)

orchestrator = Orchestrator(config=config)
```

The orchestrator binds to `tcp://*:5555`, while local CLI clients connect to `tcp://127.0.0.1:5555` by default.

<Warning title="Network exposure">
Binding to `tcp://*:5555` exposes the command interface on every network interface. Use `tcp://127.0.0.1:5555` when the interface should only be reachable from the same machine.
</Warning>

## Command Syntax

```bash
pyorchestrate <command> [arguments] [options]
```

Most runtime commands accept:

- `--socket ZMQ_ADDRESS`: ZeroMQ address used by the client. Default: `tcp://127.0.0.1:5555`
- `--format {table,json}`: Output format. Default: `table`

The option is named `--socket` for CLI compatibility, but its value is a ZeroMQ TCP address rather than a filesystem socket path.

## Output Formats

Table output is designed for interactive use:

```bash
pyorchestrate ps
```

JSON output is useful for scripts:

```bash
pyorchestrate ps --format json
```

Successful JSON responses contain the command data directly, without an outer `status` or `data` wrapper:

```json
{
  "agents": [],
  "running_count": 0,
  "max_workers": 5,
  "waiting_count": 0
}
```

Errors retain their structured error response.

## Available Commands

| Command | Purpose |
|---|---|
| `ps` | List registered agents and their current state |
| `status` | Show orchestrator status or the status of one agent |
| `dependencies` | Show registered agent dependencies |
| `start` | Start a registered agent |
| `stop` | Stop a registered agent |
| `commands` | List commands allowed by the current orchestrator configuration |
| `history` | Read recent orchestrator events |
| `history-stats` | Show aggregated event statistics |
| `stats` | Continuously refresh agent resource statistics |
| `shutdown` | Request a graceful orchestrator shutdown |

## `ps`

List all registered agents:

```bash
pyorchestrate ps [--socket ZMQ_ADDRESS] [--format {table,json}]
```

Table output includes the agent name, whether it is alive, whether it has been started, and whether it is waiting in the worker queue.

## `status`

Show overall orchestrator status:

```bash
pyorchestrate status [--socket ZMQ_ADDRESS] [--format {table,json}]
```

Show one agent:

```bash
pyorchestrate status AGENT_NAME [--socket ZMQ_ADDRESS] [--format {table,json}]
```

<Warning title="Current agent-status limitation">
The no-argument form is operational. In the current source, the agent-specific handler still reads the removed `orchestrator.dependencies` attribute instead of `orchestrator.dependency_graph.dependencies`, so `status AGENT_NAME` can return an internal error even for a registered agent.
</Warning>

An orchestrator JSON response has this shape:

```json
{
  "total_agents": 3,
  "running_agents": 2,
  "max_workers": 5,
  "waiting_agents": 1,
  "command_interface_enabled": true,
  "command_zmq_address": "tcp://*:5555"
}
```

## `dependencies`

Show the dependency mapping for all registered agents:

```bash
pyorchestrate dependencies [--socket ZMQ_ADDRESS] [--format {table,json}]
```

<Warning title="Current dependencies limitation">
The current command handler also reads the removed `orchestrator.dependencies` attribute. Until that source defect is corrected, use `orchestrator.dependency_graph.dependencies` from in-process code; the CLI command can return an internal error.
</Warning>

## `start`

Start a registered agent:

```bash
pyorchestrate start AGENT_NAME [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The agent name is required for the operation to succeed.

## `stop`

Stop a registered agent:

```bash
pyorchestrate stop AGENT_NAME [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The agent name is required for the operation to succeed.

## `commands`

Inspect the command permissions applied by `allowed_commands`:

```bash
pyorchestrate commands [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The result includes allowed commands, restricted commands, and whether restrictions are active.

## `history`

Read recent events from the orchestrator event store:

```bash
pyorchestrate history \
  [--last N] \
  [--agent AGENT_NAME] \
  [--type EVENT_NAME] \
  [--after-seq SEQUENCE] \
  [--socket ZMQ_ADDRESS] \
  [--format {table,json}]
```

Options:

- `--last N`: Maximum number of recent events. The backend default is `100`
- `--agent AGENT_NAME`: Return events for one agent
- `--type EVENT_NAME`: Return events with one event name
- `--after-seq SEQUENCE`: Return events after a sequence number

Each event returned as JSON includes `seq`, `timestamp`, `t_wall`, `t_mono_ns`, `category`, `event_name`, `agent`, `severity`, and `data`.

Event names are stored as lowercase enum values, for example `agent_registered` and `agent_started`.

<Warning title="History is not a complete lifecycle log">
The current `MessageRouter` emits agent lifecycle events through the underlying `EventManager`, bypassing `EventStore`. Registration events and explicit `orchestrator.event_bus.emit(...)` calls are recorded, but routed start, ready, heartbeat, error and termination events are not automatically present.
</Warning>

## `history-stats`

Show aggregated event-store statistics:

```bash
pyorchestrate history-stats \
  [--agent AGENT_NAME] \
  [--socket ZMQ_ADDRESS] \
  [--format {table,json}]
```

Use `--agent` to limit the statistics to one agent.

## `stats`

Continuously refresh resource statistics for registered agents:

```bash
pyorchestrate stats [--socket ZMQ_ADDRESS] [--interval SECONDS]
```

The default refresh interval is `2.0` seconds. Press `Ctrl+C` to stop monitoring.

Unlike the other runtime commands, `stats` does not expose `--format`; it renders a continuously refreshed table.

## `shutdown`

Request graceful shutdown of the orchestrator:

```bash
pyorchestrate shutdown [--socket ZMQ_ADDRESS] [--format {table,json}]
```

The command sets the orchestrator shutdown request and returns immediately.

## Connecting to a Different Address

Use the same TCP endpoint configured by the orchestrator. For a local-only listener:

```python
config = Orchestrator.Config(
    enable_command_interface=True,
    command_zmq_address="tcp://127.0.0.1:5555",
)
```

```bash
pyorchestrate status --socket tcp://127.0.0.1:5555
```

For a remote orchestrator, replace the client host with the server address:

```bash
pyorchestrate status --socket tcp://192.0.2.10:5555
```

Ensure the bind address, firewall, and command permissions match the intended exposure.

## Automation Example

Because successful JSON output contains the command data directly, query fields from the root object:

```bash
STATUS=$(pyorchestrate status --format json)
RUNNING=$(echo "$STATUS" | jq '.running_agents')
TOTAL=$(echo "$STATUS" | jq '.total_agents')

echo "Running agents: $RUNNING/$TOTAL"
```

## Troubleshooting

### Cannot connect

Confirm that:

1. the orchestrator process is running;
2. `enable_command_interface` is `True`;
3. the client address points to the configured ZeroMQ port;
4. the port is reachable through the local firewall.

Test the default local endpoint:

```bash
pyorchestrate status --socket tcp://127.0.0.1:5555
```

Check whether a process is listening on the port:

```bash
lsof -nP -iTCP:5555 -sTCP:LISTEN
```

### Command rejected

Inspect the active permissions:

```bash
pyorchestrate commands --socket tcp://127.0.0.1:5555
```

Then update `allowed_commands` in `Orchestrator.Config` if the rejected operation should be permitted.
