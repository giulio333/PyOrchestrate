# Communication Plugins

Communication plugins in PyOrchestrate allow agents to interact with other agents, external systems, and more.

## Using Communication Plugins: Automatic vs Manual Management

PyOrchestrate provides two main ways to use communication plugins in your agents:

### 1. Automatic Initialization/Finalization (Recommended)

By defining your plugins inside the `Plugin` inner class of your agent, PyOrchestrate will automatically handle their initialization and finalization during the agent's lifecycle. This is the recommended approach for most use cases.

**Example:**

```python
from PyOrchestrate.core.agent import BaseProcessAgent
from PyOrchestrate.core.plugins import ZeroMQPubSub
import zmq

class MyAgent(BaseProcessAgent):
    class Plugin(BaseProcessAgent.Plugin):
        zmq = ZeroMQPubSub("tcp://localhost:5555", zmq.PUB)

    plugin: Plugin

    def execute(self):
        super().execute()
        self.plugin.zmq.send("Hello, World!".encode())
```

---

### 2. Manual Initialization/Finalization

Alternatively, you can instantiate plugins directly in your agent (outside the `Plugin` class). In this case, you are responsible for manually initializing and finalizing the plugin.

**Example:**

```python
from PyOrchestrate.core.agent import BaseProcessAgent
from PyOrchestrate.core.plugins import ZeroMQPubSub
import zmq

class MyAgent(BaseProcessAgent):
    def __init__(self, **kwargs):
        super().__init__(**kwargs)
        self.zmq = ZeroMQPubSub("tcp://localhost:5555", zmq.PUB)
        self.zmq.initialize()  # Manual initialization

    def execute(self):
        super().execute()
        self.zmq.send("Hello, World!".encode())

    def on_close(self):
        super().on_close()
        self.zmq.finalize()  # Manual finalization
```

**Notes:**
- Overriding `__init__` must keep `**kwargs` and forward them to `super()`. The
  orchestrator constructs the agent when it *starts* it, passing `name`,
  `config`, `plugin`, `control_events`, `state_events` and `generation_id`. With
  a bare `def __init__(self)`, `register_agent` still succeeds and the failure
  only appears at startup, as a logged
  `Failed to start agent 'my_agent': MyAgent.__init__() got an unexpected keyword argument 'name'` —
  the agent never runs.
- You must call `initialize()` on the plugin before using it.
- You must call `finalize()` on the plugin when the agent is shutting down.
- Resource management is your responsibility.
- Both calls are idempotent: `initialize()` returns immediately when the plugin is already initialized, and `finalize()` does nothing when `initialize()` never ran or failed.

---

<Tip>
Automatic management via the `Plugin` class is recommended for most scenarios. Manual management is useful for advanced or custom setups where you need more control over plugin lifecycle.
</Tip>

## What the plugins share

[PubSub](/learn/agents/plugins/zeromqpubsub/zeromqpubsub), [ReqRep](/learn/agents/plugins/zeromqreqrep/zeromqreqrep), [PushPull](/learn/agents/plugins/zeromqpushpull/zeromqpushpull), [RouterDealer](/learn/agents/plugins/zeromqrouterdealer/zeromqrouterdealer) and [Pair](/learn/agents/plugins/zeromqpair/zeromqpair) all own exactly one ZeroMQ socket, and they inherit that behaviour from `ZeroMQSocketPlugin`: the `socket` property that raises until `initialize()` has run, `send()` and `recv()` with their `blocking` flag, `setsockopt()`, and the `finalize()` that closes the socket and terminates the context it created.

What each one adds is the part that is genuinely its own:

| Plugin | On top of the shared base |
| --- | --- |
| `ZeroMQPubSub` | binds PUB / connects SUB, and moves the topic in a separate frame — `send()` takes a `topic`, `recv()` drops it |
| `ZeroMQReqRep` | connects REQ / binds REP |
| `ZeroMQPushPull` | binds PUSH / connects PULL, and refuses the direction the socket cannot serve |
| `ZeroMQRouterDealer` | binds ROUTER / connects DEALER, plus `send_multipart()` and `recv_multipart()` for the identity frame |
| `ZeroMQPair` | binds or connects a PAIR socket according to `bind` |

[ZeroMQPoller](/learn/agents/plugins/zeromqpoller/zeromqpoller) is not in the table because it owns no socket of its own: it watches the sockets the others expose.

See [/api/plugins](/api/plugins) for the full signatures.

## Sharing one context

ZeroMQ expects a single `zmq.Context` per process, and every socket plugin takes one as its optional `context` argument. Pass the same context to all of them and they share it; leave the argument out and each plugin builds one of its own.

Ownership follows that argument, and it decides what `finalize()` tears down:

| `context` argument | Who owns the context | What `finalize()` does |
| --- | --- | --- |
| omitted | the plugin | closes the socket, then terminates the context |
| a context you pass | you | closes the socket, and leaves the context running |

```python
import zmq
from PyOrchestrate.core.plugins import ZeroMQPubSub, ZeroMQPushPull

context = zmq.Context()

publisher = ZeroMQPubSub("tcp://*:5556", zmq.PUB, context=context)
results = ZeroMQPushPull("tcp://*:5557", zmq.PUSH, context=context)

# ... initialize(), use, then finalize() both plugins ...

context.term()  # yours to terminate, once every socket on it is closed
```

<Warning title="Terminate a shared context last">
`zmq.Context.term()` blocks until every socket in the context is closed. Call it once, after finalizing every plugin that uses it — the plugins of a `Plugin` class are finalized one attribute at a time, so terminating it earlier would wait on the sockets the remaining plugins still hold.
</Warning>

## Writing your own socket plugin

ZeroMQ has socket types this module does not wrap. Subclass `ZeroMQSocketPlugin` and implement `initialize()` — that is the only abstract method, and everything above comes with it:

```python
import zmq
from PyOrchestrate.core.plugins import ZeroMQSocketPlugin


class ZeroMQXPubXSub(ZeroMQSocketPlugin):

    def initialize(self):
        if self._initialized:
            return

        self._socket = self.context.socket(zmq.XPUB)
        self._socket.bind(self.address)

        self._initialized = True
```

The constructor you inherit takes `address`, an optional `context` and an optional `hwm`, and creates no socket: building the plugin in a parent process that will fork is safe, because the socket only comes into existence when `initialize()` runs.

<Warning title="Return early when already initialized">
`initialize()` is called for you by the plugin manager, and may be called again by your own code. Without the `if self._initialized: return` guard a second call leaks the first socket.
</Warning>

A plugin that never needs to reach back to its agent does not have to define `set_owner()`: the default implementation ignores the owner. Override it when you want the reference, as the [heartbeat plugin](/examples/advanced/heartbeat-plugin) does.
