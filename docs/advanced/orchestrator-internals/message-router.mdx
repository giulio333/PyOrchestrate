# MessageRouter

`MessageRouter` owns a background `ChannelHandler` that reads agent `STATUS` messages from the orchestrator's process-backed `MessageChannel` and emits corresponding callbacks through an `EventManager`.

## Current mapping

| `ServiceMessage.payload["event"]` | Emitted event | Callback data |
|---|---|---|
| `agent_started` | `OrchestratorEvent.AGENT_STARTED` | `agent_name` |
| `agent_ready` | `OrchestratorEvent.AGENT_READY` | `agent_name` |
| `agent_close` | `OrchestratorEvent.AGENT_TERMINATED` | `agent_name` |
| `agent_heartbeat` | `OrchestratorEvent.AGENT_HEARTBEAT` | `agent_name` |
| `agent_error` (or legacy `ERROR`) | `OrchestratorEvent.AGENT_ERROR` | `agent_name`, `error_message` |

Messages whose top-level type is not `STATUS`, and unknown event values, are logged and ignored.

These messages are notifications, not lifecycle control commands. In
particular, receiving `agent_close` marks the router generation as terminated
and emits a callback, but worker capacity is released separately after
`Orchestrator.join()` observes that the concrete thread or process is no longer
alive.

## Construction and lifecycle

The orchestrator constructs and starts the router automatically:

```python
self.message_router = MessageRouter(
    self.event_bus,
    self.msg_channel,
    self.logger,
)
self.message_router.start()
```

The relevant methods are:

```python
router.start()
router.is_running()
router.stop(timeout=2.0)
```

`stop()` signals the internal `ChannelHandler`, waits up to the supplied timeout, then drops the handler reference. The implementation does not promise that every queued message will be processed before return.

## Shutdown of the polling thread

The `ChannelHandler` polls in a daemon thread, so it never keeps the
interpreter alive. Two rules keep that thread from turning a normal exit into a
crash — they apply to every handler, including the one the
[CommandInterface](/advanced/orchestrator-internals/command-interface) owns:

- **A closed channel ends the loop.** When `receive()` raises because the queue
  handle or the ZeroMQ socket is gone, the handler leaves the loop and logs a
  single `debug` line. It does not log an error and try again, which would
  repeat the same failure once per poll.
- **`atexit` stops whatever is left.** A handler still running when the
  interpreter starts exiting is signalled and joined by an `atexit` hook,
  registered when the handler starts. Applications that never call
  `Orchestrator.join()` or `router.stop()` therefore still shut down cleanly.

Nothing is written to the log while the interpreter is finalizing: at that
point `stderr` may be half torn down, and writing to it aborts the process
instead of ending it.

<Note>
  Calling `stop()` is still the way to end a router: the `atexit` hook is a
  backstop, and a handler that reaches it has been polling a channel nobody
  reads for as long as the application ran.
</Note>

## Generation filtering

Every lifecycle-created instance receives a monotonically increasing
`generation_id`. Before startup, the lifecycle manager activates the pair
`(agent_name, generation_id)` in the router. All status messages from an older
generation are ignored, including late close, ready, error, and heartbeat
messages.

```python
router.activate_generation("worker", 2)
router.mark_agent_terminated("worker", 2)
router.is_agent_terminated("worker", 2)    # True
router.get_terminated_agents()             # returns a copy
```

Legacy messages without a generation are accepted only when no active
generation has been registered for that name.

Activating a new generation removes termination records for older generations
of the same agent name. The router therefore retains only current termination
state rather than accumulating one tuple for every restart.

## Event history

The constructor accepts an `OrchestratorEventBus`, and every routed event goes
through `OrchestratorEventBus.emit()`. Each one therefore reaches both the
registered callbacks and `EventStore`, so routed start, ready, heartbeat, error
and termination events appear in CLI `history` and in `get_agent_timeline()`.

`agent_error` is recorded with severity `ERROR` and carries the reported
message under `data.error_message`; the other lifecycle events are recorded as
`INFO`.

<Note>
  Passing the bare `event_bus.event_manager` still works — it also exposes
  `emit()` — but such a router triggers callbacks without recording anything in
  history. Pass the bus.
</Note>

## Message shape

Agents normally create messages with:

```python
from PyOrchestrate.core.utilities.messaging import ServiceMessage

message = ServiceMessage.create_status(
    sender="worker",
    status="ready",
    event_name="agent_ready",
    generation_id=2,
)
```

The router reads `msg.type`, `msg.sender`, and the `event`, `generation_id`, and
optional `message`/`error` keys in `msg.payload`.
