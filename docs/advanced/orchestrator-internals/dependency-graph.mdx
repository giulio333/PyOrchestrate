# DependencyGraph

`DependencyGraph` stores relationships of the form “agent A depends on agents B
and C”, validates those names, detects cycles, and computes a topological
startup order.

## Declare Dependencies

Register every referenced agent, then declare the relationships:

```python
orchestrator.register_agent(DatabaseAgent, "database")
orchestrator.register_agent(CacheAgent, "cache")
orchestrator.register_agent(ApiAgent, "api")

orchestrator.add_dependency("cache", ["database"])
orchestrator.add_dependency("api", ["database", "cache"])
```

`orchestrator.start()` validates the graph automatically.

## Validation

The graph rejects:

- a dependent agent that is not registered;
- a dependency name that is not registered;
- direct or indirect dependency cycles.

Validate explicitly when useful:

```python
orchestrator.validate_dependencies()
```

Examples of invalid graphs:

```python
# Missing registered dependency
orchestrator.add_dependency("worker", ["missing-database"])
```

```python
# Cycle
orchestrator.add_dependency("agent-a", ["agent-b"])
orchestrator.add_dependency("agent-b", ["agent-a"])
```

Both cases raise `ValueError` during validation.

## Topological Ordering

After validation:

```python
registered_names = {"database", "cache", "api"}
order = orchestrator.dependency_graph.topological_sort(registered_names)
```

Every dependency appears before its dependent. Independent agents can appear in
any valid order because the orchestrator supplies registered names as a set.
Do not use registration order as a priority mechanism.

## Ordering Is Not Readiness

The dependency graph orders **start requests**. It does not wait until a
dependency is ready, healthy, or finished.

For the example:

```text
database -> cache -> api
```

the orchestrator submits `database` before `cache`, and `cache` before `api`.
When worker slots are available, all three can still be running concurrently.

`AgentLifecycleManager.start_agent()` never waits for `ready_event`, so a
dependent may enter its own startup while its dependency is still executing
`setup()`. It waits for `start_event` only if the caller supplied a
`StateEvents` object at registration; with default internally created events,
it returns after starting the thread or process.

When readiness is required, add an explicit application-level barrier, for
example a shared event or a service health check:

```python
class ApiAgent(PeriodicProcessAgent):
    def setup(self):
        super().setup()
        if not self.database_ready.wait(timeout=30):
            raise RuntimeError("database did not become ready")
```

Pass the shared synchronization primitive when registering the agent.

## Interaction with WorkerPoolScheduler

`Orchestrator.start()` performs:

```text
validate dependency graph
        |
        v
compute topological order
        |
        v
submit each name to WorkerPoolScheduler
        |
        +--> start immediately when a slot is free
        |
        +--> queue when the pool is full
```

The queue preserves the order in which names are submitted. It does not infer
additional readiness conditions.

## Direct Graph API

```python
graph = orchestrator.dependency_graph

graph.get_dependencies("api")
graph.has_dependencies()
```

The current public methods are:

```text
add_dependency(agent_name, depends_on)
validate(valid_agent_names)
topological_sort(agent_names)
get_dependencies(agent_name)
has_dependencies()
```
