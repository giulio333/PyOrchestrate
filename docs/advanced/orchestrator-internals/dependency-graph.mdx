# DependencyGraph

`DependencyGraph` stores relationships of the form “agent A depends on agents B
and C”, validates those names, detects cycles, and computes a topological
startup order.

## Declare Dependencies

Register every referenced agent, then declare the relationships:

```python
orchestrator.register_agent(DatabaseAgent, "database")
orchestrator.register_agent(CacheAgent, "cache")
orchestrator.register_agent(ApiAgent, "api")

orchestrator.add_dependency("cache", ["database"])
orchestrator.add_dependency("api", ["database", "cache"])
```

`orchestrator.start()` validates the graph automatically.

## Validation

The graph rejects:

- a dependent agent that is not registered;
- a dependency name that is not registered;
- direct or indirect dependency cycles.

Validate explicitly when useful:

```python
orchestrator.validate_dependencies()
```

Examples of invalid graphs:

```python
# Missing registered dependency
orchestrator.add_dependency("worker", ["missing-database"])
```

```python
# Cycle
orchestrator.add_dependency("agent-a", ["agent-b"])
orchestrator.add_dependency("agent-b", ["agent-a"])
```

Both cases raise `ValueError` during validation.

## Topological Ordering

After validation:

```python
registered_names = {"database", "cache", "api"}
order = orchestrator.dependency_graph.topological_sort(registered_names)
```

Every dependency appears before its dependent. Independent agents can appear in
any valid order because the orchestrator supplies registered names as a set.
Do not use registration order as a priority mechanism.

Sorting reads the graph without modifying it: an agent that declares no
dependency stays out of `dependency_graph.dependencies`, before and after
`Orchestrator.start()`. That is the mapping the [`dependencies`](/cli/runtime-commands#dependencies)
command reports, and what `has_dependencies()` answers about.

## Ordering Is Not Readiness

The dependency graph orders **start requests**. It does not wait until a
dependency is ready, healthy, or finished.

For the example:

```text
database -> cache -> api
```

the orchestrator submits `database` before `cache`, and `cache` before `api`.
When worker slots are available, all three can still be running concurrently.

`AgentLifecycleManager.start_agent()` never waits for `ready_event`, so a
dependent may enter its own startup while its dependency is still executing
`setup()`. It waits for `start_event` for both caller-supplied and default
event containers.

When readiness is required, add an explicit application-level barrier, for
example a shared event or a service health check. The dependency below still
orders the two start requests; the event is what makes the API wait:

```python
import multiprocessing

class Database(PeriodicProcessAgent):
    def setup(self):
        super().setup()
        time.sleep(2)                 # whatever makes it slow to become usable
        self.database_ready.set()     # releases everyone waiting on the barrier

class Api(PeriodicProcessAgent):
    def setup(self):
        super().setup()
        if not self.database_ready.wait(timeout=30):
            raise RuntimeError("database did not become ready")

database_ready = multiprocessing.Event()

orchestrator.register_agent(Database, "database", database_ready=database_ready)
orchestrator.register_agent(Api, "api", database_ready=database_ready)
orchestrator.add_dependency("api", ["database"])
```

Its log shows both halves of the distinction. The API is started 80 milliseconds
after the database, long before the database is usable — that is the ordering.
It then sits on the barrier for two seconds and resumes on the very timestamp of
the `set()` — that is the readiness:

```text
10:13:39.343 | INFO | Orchestrator | Agent 'database' started successfully.
10:13:39.422 | INFO | Orchestrator | Agent 'api' started successfully.
10:13:39.430 | INFO | api          | waiting for the database
10:13:41.368 | INFO | database     | ready, other agents may proceed
10:13:41.369 | INFO | api          | database is ready, starting to serve
```

Three things about this pattern are worth knowing before you write your own.

**The keyword argument becomes an attribute on its own.** Extra keyword
arguments to `register_agent()` reach `BaseAgent.__init__()` and are stored as
instance attributes, which is why `database_ready=database_ready` is readable as
`self.database_ready` inside the agent. The name of the argument is the name of
the attribute.

**Blocking in `setup()` does not trip `agent_start_timeout`.** The agent sets
`state_events.start_event` before calling `setup()`, and
`AgentLifecycleManager.start_agent()` waits for exactly that event: the
orchestrator has already logged the agent as started while it sits on the
barrier. The 30 seconds above are therefore unrelated to the orchestrator's own
start timeout. When the barrier does expire, raising is handled like any other
failure in `setup()` — the agent terminates with a `critical` status and emits
`AGENT_ERROR`.

<Warning title="Match the primitive to the agent type">
Process agents need a `multiprocessing.Event`; a `threading.Event` cannot be
pickled into them and the failure names neither the event nor the agent that
holds it:

```text
ERROR | Orchestrator | Failed to start agent 'database': cannot pickle '_thread.lock' object
```

Thread agents are the other way round: a `threading.Event` is enough, and a
`multiprocessing.Event` costs a system semaphore for nothing.
</Warning>

A runnable version of this example lives in
[`examples/example_readiness_barrier.py`](https://github.com/giulio333/PyOrchestrate/blob/main/examples/example_readiness_barrier.py).

## Interaction with WorkerPoolScheduler

`Orchestrator.start()` performs:

```text
validate dependency graph
        |
        v
compute topological order
        |
        v
submit each name to WorkerPoolScheduler
        |
        +--> start immediately when a slot is free
        |
        +--> queue when the pool is full
```

The queue preserves the order in which names are submitted. It does not infer
additional readiness conditions.

## Direct Graph API

```python
graph = orchestrator.dependency_graph

graph.get_dependencies("api")
graph.has_dependencies()
```

The current public methods are:

```text
add_dependency(agent_name, depends_on)
validate(valid_agent_names)
topological_sort(agent_names)
get_dependencies(agent_name)
has_dependencies()
```
