# Message Channel

`MessageChannel` transports `ServiceMessage` objects through a thread queue, a process queue, or ZeroMQ. It is an internal framework API; application-level agent communication should normally use the [Communication Plugins](/learn/agents/plugins/communication-plugins).

## Channel types

| `a_type` | Backend | Current use |
|---|---|---|
| `thread` | `queue.Queue` | Available to internal/custom components |
| `process` | `multiprocessing.Queue` | Agent status messages to the orchestrator |
| `zmq_router` | ZeroMQ ROUTER | Orchestrator command server |
| `zmq_dealer` | ZeroMQ DEALER | CLI/web command client |

`Orchestrator` creates its agent channel with `MessageChannel("process")` regardless of whether an individual agent class uses a thread or a process.

## ServiceMessage

```python
from PyOrchestrate.core.utilities.messaging import ServiceMessage

status = ServiceMessage.create_status(
    sender="worker",
    status="ready",
    event_name="agent_ready",
)

command = ServiceMessage.create_command(
    sender="client",
    command="status",
    args=[],
)
```

When a `STATUS` message is sent through `BaseAgent.send_message()`, the agent's
current non-zero `generation_id` is added automatically if the payload does not
already contain one. An explicit generation is preserved. This keeps custom
agent and plugin status messages compatible with generation-aware routing.

The orchestrator's process queue carries agent-to-orchestrator status
notifications. Startup acknowledgement and cooperative stop control use shared
state/control events instead: `start_event` releases the startup wait and
`stop_event` requests agent termination. Start and stop are not sent to the
agent through this queue.

The serialized envelope contains:

| Field | Description |
|---|---|
| `sender` | Sender identifier |
| `event_name` | Serialized value of `ServiceMessage.type`: `COMMAND` or `STATUS` |
| `payload` | Message-specific dictionary |
| `timestamp` | ISO-formatted creation time |

`to_json()`, `to_bytes()` and `from_bytes()` provide serialization helpers. `to_bytes()` adds a trailing newline, but ZeroMQ sends the JSON representation as transport frames rather than as a line-delimited stream.

## Send and receive

```python
from PyOrchestrate.core.utilities.messaging import MessageChannel

channel = MessageChannel("thread")
channel.send("ignored-for-queues", status)
received = channel.receive(timeout=1.0)
channel.close()
```

For queue channels, `target` is ignored and `receive()` returns `None` on timeout. `close()` has no queue-specific cleanup.

For a DEALER command client:

```python
client = MessageChannel(
    "zmq_dealer",
    "tcp://127.0.0.1:5555",
)
response = client.send_and_receive(command, timeout=5.0)
client.close()
```

`send_and_receive()` is only valid for `zmq_dealer`; otherwise it raises `ValueError`. The `auto_close` argument defaults to `False`.

## Current guarantees and limits

- Constructors restrict `a_type` to the four supported literal values.
- `ServiceMessage.from_bytes()` raises on malformed JSON, missing fields or invalid timestamps.
- The lower-level ZeroMQ receive path catches malformed envelopes and returns `None`.
- A generated `request_id` is carried in command payloads, but `MessageChannel` itself does not match multiple outstanding responses by that ID.
- No message-size limit is enforced by this class.
- `close()` uses ZeroMQ `LINGER=0`; it does not drain pending application messages.
- A ROUTER reply is sent to the identity from its most recent receive operation.

These details matter when reusing the utility directly; the supported CLI/web command path serializes requests through `CommandInterface`.
